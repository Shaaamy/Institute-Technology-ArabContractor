📋 Project Overview INTRO

ICMET (المعهد التكنولوجي) is a full-stack web application for a technology institute that provides online and onsite training programs. The system allows students to browse, purchase, and enroll in courses, while admins manage the full operational lifecycle including courses, users, payments, refunds, attendance, and certificates.
🎯 Purpose
  • Online course catalog & enrollment
  • Secure payment via Bank Misr
  • Certificate management & upload
  • Refund request & processing
  • Admin operations dashboard
  • News, library, and media management
👥 User Types
  • Public visitor — browses the site, no login needed
  • Registered student — can purchase courses, view enrollments, request refunds
  • Admin — full control panel for all system operations
🏗️ Architecture Pattern
  • SPA (Single Page Application) frontend
  • REST API backend (no server-side rendering)
  • Clean Architecture — 4 distinct layers
  • JWT stateless authentication
  • Azure cloud-native deployment

⚛️ Frontend Project Structure FRONTEND

The frontend is a React 18 SPA built with Vite. All source code lives under src/Frontend/icmet-website/src/. The app is served as static files and communicates with the backend exclusively via REST API calls. There is no SSR (Server-Side Rendering).

Folder Structure

🏛️ Backend — Clean Architecture BACKEND

The backend solution Institute.Web.sln follows Clean Architecture — the codebase is split into 4 projects, each with a distinct responsibility. Dependencies only flow inward: outer layers depend on inner layers, never the reverse. This ensures the business logic (Domain + Application) has zero dependency on ASP.NET or SQL Server.

Layer Responsibilities

Institute.Web solution — 4 projects

🌐
Institute.API
Presentation
Entry point — Program.cs bootstraps everything: registers services, configures middleware (CORS, auth, Swagger), sets up EF migrations, and starts Kestrel. Hosts all Controllers. Contains appsettings.json with connection strings, JWT config, and Azure Blob settings. This is the only project that references ASP.NET directly.
⚙️
Institute.Application
Business Logic
Contains all use cases (services / command handlers). Uses AutoMapper to map between Domain entities and DTOs that are sent to the client. Contains validators, business rules, and orchestration logic. Has no knowledge of HTTP, databases, or Azure — it only speaks in terms of interfaces defined in the Domain.
🗄️
Institute.Infrastructure
Data Access
Implements the interfaces defined in Application/Domain. Contains AppDbContext (EF Core), all Repository implementations, Azure Blob Storage service (using Azure.Storage.Blobs), and external integrations (Bank Misr payment gateway, Svix webhooks). EF migrations are managed from here.
📦
Institute.Domain
Core Entities
The innermost layer — zero external dependencies. Contains only C# classes: AppUser.cs, CoursePurchase.cs, Payment.cs, and AppDbContext.cs. These are the canonical data models. No NuGet references to ASP.NET, EF, or Azure.
💡 The dependency rule: Domain ← Application ← Infrastructure ← API. If you need to swap SQL Server for PostgreSQL, only Infrastructure changes. If you need to swap ASP.NET for a CLI tool, only the API project changes. The business logic stays untouched.

🔐 Authentication & Authorization AUTH

The system uses stateless JWT (JSON Web Token) authentication via Microsoft.AspNetCore.Authentication.JwtBearer. Passwords are hashed server-side before storage. Tokens carry role claims (Admin or User) and are validated on every protected API request — without hitting the database on each call.

Login Flow — Step by Step

From browser to protected resource

1

User submits Login.jsx form

Frontend sends POST /api/auth/login with { email, password }.

2

API validates credentials

The API looks up the user in the AppUsers table by email, then verifies the hashed password. If no match → 401 Unauthorized. Roles are resolved via UserPermissions → Permissions.

3

JWT is generated & signed

Server creates a token with claims: userId, email, role (Admin or User). Token is signed with the secret key from appsettings.json. Expiry: configurable (e.g., 7 days).

4

Frontend stores the token

AuthSync.jsx stores the JWT in localStorage. All subsequent API calls via api.js attach Authorization: Bearer <token>.

5

Protected API reads role from token

ASP.NET's [Authorize] attribute and [Authorize(Roles = "Admin")] validate the token signature and role on every request — no DB lookup needed.

Token Structure (JWT Payload)

Claims inside the token

// Decoded JWT payload example
{
  "sub":    "a3f2-91bc-...",   // userId (GUID)
  "email": "user@icmet.eg",
  "role":  "Admin",          // or "User"
  "iat":   1718000000,       // issued at
  "exp":   1718604800        // expires at
}
⚠️ Token Expiry & AuthSync

AuthSync.jsx runs on every page mount. It checks the JWT's exp claim against Date.now(). If expired, it clears localStorage and redirects to /login. This prevents users from seeing stale authenticated UI.

🛡️ Admin Route Guard

In DashboardLayout.jsx, React Router checks if the decoded token contains role: "Admin". If not, it redirects immediately to /login — even if a valid User token exists.

🔗 Database Relationships RELATIONS

All foreign key relationships are enforced at the database level by EF Core. The central entities are AppUsers and Planwork (courses) — almost every other table connects back to one or both. Cascades are configured to avoid accidental data loss; most status changes are soft operations.

Key Relationship Rules

15 tables — how they connect

1

AppUsers → Carts (1:N)

Each user has one active cart. Carts.UserId FK. CartItems link to both a Cart and a Planwork course.

2

AppUsers + Planwork → Orders (1:N each)

An order records who bought what. Orders.UserId links to the buyer. OrderItems holds the individual course lines with price snapshots.

3

Orders → Payments (1:1)

Each paid order has exactly one Payment record. Payments.OrderId FK. TransactionRef is critical for Bank Misr refund calls.

4

Orders → Enrollments (1:N)

On payment success, one Enrollment row is created per OrderItem. Enrollment is deleted when a refund is fully processed.

5

Orders → RefundRequests (1:N)

A user can request a refund per order+course combination. RefundRequests.OrderId + PlanworkId + UserId are the three key FKs.

6

Planwork → PlanFiles (1:N)

Each course can have multiple attached files (outlines, brochures). PlanFiles.FileId FK → Planwork.ChildID.

7

dailynews → newsPic (1:N)

Each news article can have multiple images. newsPic.PicId FK → dailynews.news_id.

8

AppUsers ↔ Permissions (M:N via UserPermissions)

Granular permissions are assigned per user via the join table UserPermissions. Allows fine-grained admin access control beyond simple roles.

🔑 Key: Orders.SuccessIndicator

On payment return, the system verifies Orders.SuccessIndicator against the value returned by Bank Misr's callback. Only if they match is the order marked Paid and enrollments created. This prevents URL manipulation attacks.

📁 File Upload Pipeline FILES

Files are never stored on the server's filesystem. All uploads go directly to Azure Blob Storage via the Azure.Storage.Blobs SDK. The returned blob URL is then saved to the database. This means the server is stateless and can be restarted or scaled without losing files.

Certificate Upload Flow

Admin → Blob Storage → DB

1

Admin opens CertUploadModal.jsx

Selects a PDF or image file from their device. The modal shows a preview and validates file type/size on the client.

2

Frontend sends multipart/form-data

POST /api/certificates/upload with the file binary and metadata (userId, courseId) as form fields. The Authorization: Bearer token is included — Admin role required.

3

API uploads to Azure Blob

The Infrastructure layer's blob service uses Azure.Storage.Blobs.BlobClient.UploadAsync(). The file is stored in a named container (e.g., certificates) with a unique GUID filename.

4

Blob URL saved to DB & returned

The public blob URL (e.g., https://<account>.blob.core.windows.net/certificates/abc123.pdf) is stored in the Certificates table and returned to the frontend.

5

User downloads via direct URL

When a user opens their certificate, the frontend links directly to the Azure Blob URL — no API proxy needed. Azure Blob serves the file directly to the browser.

💳 Payment Flow (Bank Misr) PAYMENT

Payments are processed through Bank Misr's Mastercard gateway. The system uses a redirect-based flow — the user is sent to the bank's hosted payment page, then redirected back to the system. This means ICMET never handles raw card data (PCI DSS compliant).

End-to-End Payment Flow

1

User clicks "Checkout" on ShoppingCartPage.jsx

Frontend calls POST /api/payments/checkout with course IDs and total amount.

2

API creates an order with Bank Misr

Backend calls Bank Misr's API to create a payment session. Bank returns a paymentUrl and an orderId. The system stores the pending order in the Payments table with Status = 0.

3

User is redirected to Bank's hosted page

Frontend receives the paymentUrl and redirects the browser to Bank Misr's secure payment page. User enters card details there — ICMET never sees the card number.

4

Bank redirects back to the return URL

After payment, Bank Misr redirects the browser to GET /api/payments/return?orderId=...&result=SUCCESS. The API verifies the transaction reference with the bank.

5

System confirms & creates enrollment

If verified: Payment record updated to Status = 1 (Paid), CoursePurchase record created, TransactionRef stored. User is redirected to /payment-result?success=true.

What Happens on "Sent"

The critical step

1

Admin clicks "Mark as Sent" in RefundActionModal

Frontend calls PUT /api/refund/{id}/sent.

2

API fetches the original payment

Looks up Payment.TransactionRef linked to this refund request.

3

Calls Bank Misr RefundPaymentAsync

Makes a PUT request to Bank Misr's endpoint:

PUT /order/{orderNumber}/transaction/{newRefundId}

With body: { apiOperation: "REFUND", amount: {total: X, currency: "EGP"} }

4

On SUCCESS → Enrollment deleted

EF Core deletes the CoursePurchase row (or marks Status = Refunded). User immediately loses access to the course in MyCourses.

5

On FAILURE → Manual IBAN fallback

If bank returns an error, the system keeps the refund at Approved status. Admin uses the stored IBAN + BankName fields to process the transfer manually.

👥 Roles & Permissions ROLES

Roles are stored in ASP.NET Identity tables (AspNetRoles, AspNetUserRoles) and embedded as claims inside the JWT token. There are two application roles: Admin and User. Access is enforced both on the frontend (route guards) and the backend ([Authorize(Roles="Admin")]).

How SPA + API are Served Together

💡 ASP.NET Core serves the React dist/ folder as static files. Any request to /api/* is handled by the API controllers. Any other path (e.g., /courses/5) falls through to index.html, which lets React Router handle the navigation client-side. This is the standard SPA hosting pattern on ASP.NET. 
// Program.cs (simplified)
app.UseStaticFiles();          // serves React dist/
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();          // /api/* endpoints
app.MapFallbackToFile("index.html"); // SPA fallback

✅ Production Checklist
  • JWT secret key — strong random string, stored in Azure App Service environment variables (not in code)
  • Connection string — Azure SQL, set in App Service Configuration blade
  • Blob Storage connection — use Azure Managed Identity in production (no connection string needed)
  • Bank Misr credentials — stored as App Service secrets
  • CORS policy — restrict to known frontend origin in production
  • EF Migrations — run automatically on app startup via dbContext.Database.Migrate()
